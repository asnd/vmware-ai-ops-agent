# Мониторинг DC-фабрик: варианты развития архитектуры

> Отдельный подпроект, не связан с `vmware-ai-ops-agent`. Живёт в каталоге
> `dc-fabric-monitoring/`.

## 1. Что есть сейчас и в чём проблема

```
cron (1 раз в сутки)
  └─ скрипт: SNMP-опрос таблиц алармов на каждом свитче (сотни устройств,
     десятки Clos-фабрик)
       └─ файл(ы) с активными алармами → git commit
```

| Проблема | Почему это плохо |
|---|---|
| Опрос раз в сутки | Авария, начавшаяся в 09:00, видна только на следующий день |
| Скрипт stateless | Нет ответа на вопрос «что нового / что ушло с прошлого раза» |
| Нет уведомлений | Кто-то должен сам открыть репозиторий и прочитать файл |
| Нет статистики интерфейсов | Не видно загрузку, ошибки и флапы uplink'ов Edge Leaf / DC-GW → P-роутеры |
| Zabbix/Nagios не подходят | Отдельный продукт со своей БД, UI, апгрейдами и шаблонами |

Требования (как я их понял):

1. Опрашивать чаще (минуты, а не сутки).
2. Видеть **дельту**: новые, ушедшие (cleared) и изменившиеся алармы относительно
   предыдущего опроса и за сутки.
3. Отправлять **новые** алармы в e-mail и/или Teams (webhook).
4. Для Edge Leaf и DC-GW — хотя бы приблизительные графики/статистика по
   uplink'ам к IP-бэкбону (P-роутерам).
5. Минимум новой инфраструктуры и ручного администрирования.

## 2. Ключевая идея, общая для всех вариантов: «состояние + дельта»

Независимо от выбранного варианта, нужно перейти от «снимка» к «жизненному циклу
аларма». Для этого у каждого аларма должен быть **стабильный ключ**:

```
alarm_key = hash(device, alarm_type/OID, resource (ifName, PSU, fan …), normalized_text)
```

Из `normalized_text` вырезаются таймстемпы, счётчики и прочие меняющиеся поля,
иначе каждый опрос будет давать «новый» аларм.

Сравнение текущего опроса с предыдущим состоянием даёт три множества:

| Событие | Условие | Действие |
|---|---|---|
| `NEW` | ключ есть сейчас, не было раньше | уведомить (после подтверждения, см. ниже) |
| `CLEARED` | ключ был, сейчас нет | уведомить «resolved» (опционально) |
| `CHANGED` | ключ есть в обоих, но изменилась severity | уведомить |

Две защиты от шума:

* **Подтверждение (confirm / hold-down)** — аларм считается новым, только если
  он виден в N опросах подряд (например, 2 × 5 мин). Убирает краткие флапы.
* **Задержка снятия (clear-after)** — аларм считается снятым, только если его нет
  в M опросах подряд. Убирает «пропал на один опрос из-за таймаута SNMP».
* **Недоступность устройства ≠ снятие алармов.** Если свитч не ответил по SNMP,
  его алармы не трогаем, а генерируем отдельное событие `DEVICE_UNREACHABLE`.

Уведомления **группируются** по фабрике/роли (один пост в Teams «Fabric DC1-F07:
+3 новых, −1 снятый», а не 50 отдельных сообщений), плюс ежедневный дайджест.

> **Про Teams:** классические Office 365 Connectors («Incoming Webhook»)
> Microsoft выводит из эксплуатации. Для новых интеграций используйте
> **Workflows (Power Automate) → «When a Teams webhook request is received»** и
> отправляйте Adaptive Card. Прототип в этом каталоге делает именно так.

## 3. Вариант A — «Эволюция текущего скрипта» (без новой инфраструктуры)

Оставляем cron + Python + git, но делаем скрипт stateful.

```
cron / systemd timer (каждые 5 мин)
  ├─ poll_alarms   — параллельный SNMP bulkwalk (asyncio / пул потоков)
  │     └─ snapshots/<fabric>/<device>.json   (нормализовано, отсортировано)
  ├─ alarm_delta   — сравнение со state.json → NEW / CLEARED / CHANGED
  │     ├─ Teams (Workflows webhook, Adaptive Card)
  │     └─ e-mail (SMTP relay)
  ├─ git commit    — ТОЛЬКО если снимок изменился
  │
  └─ poll_ifstats (каждые 1–5 мин, только Edge Leaf / DC-GW uplinks)
        └─ IF-MIB → RRD или SQLite → статический HTML с графиками
                     (nginx / GitLab Pages / любой web-сервер)
```

### Что меняется

* **Частота.** Опрос таблиц алармов у нескольких сотен свитчей — это несколько
  сотен небольших bulkwalk'ов; при параллелизме 30–50 укладывается в десятки
  секунд. 5 минут — безопасный интервал, 1–2 минуты тоже реально.
* **Git как журнал изменений.** Снимки детерминированы (сортировка, без
  таймстемпов), коммит делается только при изменении. Тогда:
  * `git log -p --since=yesterday -- snapshots/` — дельта за сутки;
  * `git log -- snapshots/dc1-f07/` — история конкретной фабрики;
  * сообщение коммита = краткая сводка дельты (`+3 NEW, -1 CLEARED`).
* **state.json** хранит `first_seen`, `last_seen`, счётчики подтверждения и
  флаг «уже уведомили». Он маленький и тоже может лежать в git.
* **Интерфейсы uplink.** Опрашиваются только нужные порты (фильтр по
  `ifAlias`, например `/P-RTR|BACKBONE|UPLINK/`), счётчики `ifHCInOctets`,
  `ifHCOutOctets`, `ifIn/OutErrors`, `ifIn/OutDiscards`, `ifOperStatus`,
  `ifHighSpeed`. Хранение:
  * **rrdtool** — классика, фиксированный размер, графики «из коробки»; или
  * **SQLite** + небольшой генератор HTML (uPlot / Chart.js) — проще
    кастомизировать, легко посчитать 95-й перцентиль и «top-N загруженных».
  * Счётчики в git **не класть** — это анти-паттерн.
* Плюс простые пороговые алерты на uplink'и: загрузка > 80 %, рост ошибок/дропов,
  смена `ifOperStatus` — через тот же механизм дельты и уведомлений.

### Плюсы / минусы

| + | − |
|---|---|
| Ноль новых продуктов, только Python и cron | Всё самописное: графики, ретеншн, UI |
| Сохраняется git как источник истины и аудит | Только polling, задержка = интервал опроса |
| Можно сделать за 1–2 недели | Нет silences/maintenance-окон «из коробки» (придётся дописать) |
| Прототип уже лежит в этом каталоге | Масштабирование графиков на все интерфейсы — неудобно |

**Когда выбирать:** если категорически нельзя поднимать ничего, кроме скрипта
на существующей машине.

## 4. Вариант B — «Лёгкий стек-как-код»: Prometheus + snmp_exporter + Alertmanager + Grafana

Не Zabbix: нет БД с шаблонами, которые надо кликать в UI. Это 4 контейнера на
одной VM (`docker compose`), **вся конфигурация — YAML-файлы в том же git**.
Обновление = поменять тег образа.

```
                 inventory.yaml (из git / NetBox)
                         │  генерирует file_sd targets
                         ▼
┌──────────────┐   ┌──────────────┐   ┌───────────────┐   ┌──────────────┐
│ snmp_exporter│◄──│  Prometheus  │──►│ Alertmanager  │──►│ Teams / mail │
│ (IF-MIB,     │   │ или Victoria │   │ dedup, group, │   └──────────────┘
│  vendor MIBs)│   │  Metrics     │   │ silence,      │
└──────┬───────┘   └──────┬───────┘   │ inhibit       │
       │ SNMP             │           └───────▲───────┘
       ▼                  ▼                   │ POST /api/v2/alerts
   свитчи           ┌──────────┐      ┌───────┴────────┐
                    │ Grafana  │      │ alarm poller   │  ← текущий скрипт,
                    └──────────┘      │ (из варианта A)│    доработанный
                                      └────────────────┘
```

### Как закрываются требования

* **Интерфейсы uplink — сильная сторона.** snmp_exporter опрашивает IF-MIB
  раз в 30–60 с; в Grafana — `rate(ifHCInOctets[5m])*8`, утилизация в % от
  `ifHighSpeed`, ошибки, дропы, 95-й перцентиль, top-N по фабрикам.
  Через `filters` в генераторе snmp_exporter можно опрашивать только порты,
  у которых `ifAlias` совпадает с regex — это снижает нагрузку на control plane.
* **Алармы.** Два способа:
  1. **(рекомендую)** Оставить собственный Python-поллер алармов (таблицы
     алармов у вендоров разные, в Python их нормализовать проще) и отправлять
     активные алармы в **Alertmanager API** (`POST /api/v2/alerts`) на каждом
     опросе. Alertmanager сам делает дедупликацию, NEW/RESOLVED, группировку,
     повторные напоминания, silences (окна обслуживания) и маршрутизацию:
     Edge/DC-GW → дежурным в Teams, остальные → в e-mail-дайджест.
  2. Описать таблицы алармов в snmp_exporter и превратить строки в метрики
     (`vendor_alarm_active{device=…, type=…, severity=…} 1`), а правила — в
     Prometheus. Работает, но для «текстовых» алармов неудобно.
* **Уведомления.** У Alertmanager есть нативные receiver'ы `email_configs` и
  `msteamsv2_configs` (Teams Workflows, версии 0.28+).
* **Git остаётся.** Поллер может продолжать писать снимки в git (вариант A) —
  это даёт историю и аудит независимо от Prometheus.
* **Хранение.** Prometheus по умолчанию — 15 дней; для года истории —
  VictoriaMetrics single-node (один бинарник, совместим по PromQL, сжатие лучше).

### Пример ключевых конфигов

`alertmanager.yml` (фрагмент):

```yaml
route:
  receiver: noc-mail
  group_by: [fabric, alertname]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 12h
  routes:
    - matchers: [ 'role=~"edge-leaf|dc-gw"', 'severity=~"critical|major"' ]
      receiver: noc-teams
receivers:
  - name: noc-teams
    msteamsv2_configs:
      - webhook_url_file: /etc/alertmanager/teams_webhook_url
  - name: noc-mail
    email_configs:
      - to: noc@example.com
inhibit_rules:   # если свитч недоступен — не спамить его алармами
  - source_matchers: [ 'alertname="DeviceUnreachable"' ]
    target_matchers: [ 'alertname=~"Alarm.*|Uplink.*"' ]
    equal: [device]
```

Правило Prometheus для uplink'ов:

```yaml
- alert: UplinkHighUtilization
  expr: |
    max by (device, ifName, fabric) (
      rate(ifHCOutOctets{role=~"edge-leaf|dc-gw", ifAlias=~".*P-RTR.*"}[5m]) * 8
      / (ifHighSpeed * 1e6)
    ) > 0.8
  for: 15m
  labels: { severity: major }
```

### Плюсы / минусы

| + | − |
|---|---|
| Полноценные графики, PromQL, дашборды | Нужна 1 VM (4 vCPU / 8 GB / ~100 GB диска с запасом) |
| Жизненный цикл алертов, silences, inhibit — готовые | Нужно один раз собрать `snmp.yml` под ваши MIB |
| Всё — YAML в git, ревью через MR, деплой из CI | Ещё один набор контейнеров для обновления (но без БД/шаблонов в UI) |
| Индустриальный стандарт, легко найти людей | |

**Когда выбирать:** если можно выделить одну VM. Это лучший баланс
«ценность / сопровождение».

## 5. Вариант C — Event-driven: SNMP traps / syslog + gNMI streaming telemetry

Переход от опроса к событиям.

```
Свитчи ──SNMP traps / syslog──► snmptrapd / vector / rsyslog ─┐
   │                                                         ├─► нормализация ─► Alertmanager / Teams
   │                                    поллер (сверка)─────┘
   │
   └──gNMI (OpenConfig, on-change + sample 10–30 s)──► gnmic ─► Prometheus/VictoriaMetrics ─► Grafana
                                                     (или Kafka/NATS → куда угодно)
```

* **Алармы в реальном времени.** Traps/syslog приходят за секунды. Но UDP —
  с потерями, поэтому периодический поллер (вариант A) остаётся как
  **сверка** («traps для скорости, polling для истины»).
* **gNMI streaming telemetry** — современные DC-NOS (Arista EOS, Cisco NX-OS,
  Juniper Junos/Evo, Nokia SR Linux, SONiC) его поддерживают. `gnmic` — один
  бинарник, подписывается на `/interfaces/interface/state/counters`,
  `/interfaces/interface/state/oper-status` (on-change) и, где поддерживается,
  `/system/alarms`. Встроенный Prometheus-выход.
* Интерфейсная статистика с шагом 10–30 с без нагрузки на SNMP-агент.

### Плюсы / минусы

| + | − |
|---|---|
| Задержка секунды, а не минуты | Изменение конфигурации на сотнях свитчей (gNMI, TLS-сертификаты, trap/syslog targets) |
| Меньше нагрузка на control plane, чем у SNMP-polling | Поддержка OpenConfig-путей отличается у вендоров и версий NOS |
| Масштабируется на тысячи устройств | Больше движущихся частей; traps всё равно требуют сверки опросом |

**Когда выбирать:** как следующий этап после B, начиная с Edge Leaf / DC-GW,
где важна скорость реакции и детальность uplink-статистики.

## 6. Вариант D (упомянуть для полноты) — контроллер фабрики от вендора

Если фабрики построены на Arista (CloudVision), Cisco (Nexus Dashboard / NDFC),

противоречит исходному ограничению; но стоит проверить, что уже куплено.

## 7. Сравнение

| Критерий | A: скрипт + state | B: Prometheus-стек | C: traps + gNMI |
|---|---|---|---|
| Новая инфраструктура | нет | 1 VM, 4 контейнера | B + изменения на свитчах |
| Задержка обнаружения аларма | интервал опроса (1–5 мин) | 1–5 мин | секунды |
| Дельта NEW/CLEARED | своя логика | Alertmanager | Alertmanager |
| Teams / e-mail | своя логика | нативно | нативно |
| Графики uplink'ов | самописные (RRD/SQLite+HTML) | Grafana, полноценно | Grafana, высокое разрешение |
| Silences / окна обслуживания | дописывать | есть | есть |
| Трудозатраты на запуск | ~1–2 нед. | ~2–3 нед. | ~1–2 мес. (зависит от NOS) |
| Сопровождение | низкое, но всё своё | низкое (GitOps) | среднее |

## 8. Рекомендация: поэтапно, каждый этап сохраняет ценность предыдущего

1. **Этап 1 (сразу):** вариант A без графиков — поллер каждые 5 мин,
   детерминированные снимки + коммит только при изменении, `state.json`,
   дельта с confirm/clear-after, уведомления в Teams Workflows и e-mail,
   ежедневный дайджест. Прототип логики дельты — `alarm_delta.py` в этом каталоге.
2. **Этап 2:** поднять вариант B на одной VM: snmp_exporter + Prometheus
   (или VictoriaMetrics) + Grafana для uplink'ов Edge Leaf / DC-GW;
   переключить отправку уведомлений из поллера на Alertmanager API
   (получаем silences, группировку, маршрутизацию бесплатно).
3. **Этап 3:** для Edge Leaf / DC-GW включить gNMI (gnmic → тот же
   Prometheus) и syslog/traps → нормализатор → Alertmanager. Поллер остаётся
   как сверка.

На всех этапах:

* **Инвентарь — один файл** (`inventory.yaml` или NetBox): устройство → фабрика,
  роль (`spine`, `leaf`, `edge-leaf`, `dc-gw`), вендор, SNMP-профиль. Из него
  генерируются цели опроса, labels для алертов и маршрутизация уведомлений.
* **Секреты** (SNMP community/v3, webhook URL, SMTP) — не в git, а в
  переменных окружения / vault / файлах с правами 600.
* **Мониторинг самого мониторинга:** если поллер не отработал N циклов —
  отдельное уведомление («dead man's switch»).
* **SNMPv3** вместо v2c, если ещё не используется.

## 9. Что нужно уточнить, чтобы двигаться дальше

1. Вендоры и версии NOS свитчей (определяет MIB алармов и поддержку gNMI).
2. Формат текущих файлов, которые пишет cron-скрипт (адаптер в `alarm_delta.py`).
3. Можно ли выделить одну VM/контейнерный хост (вариант B)?
4. Как идентифицировать uplink'и к P-роутерам: по `ifAlias`, по LLDP-соседу, по
   списку в инвентаре?
5. Teams: можно ли создать Workflow с webhook-триггером в нужном канале?
   E-mail: есть ли SMTP relay?
